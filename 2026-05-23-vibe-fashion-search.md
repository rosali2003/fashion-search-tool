## Foundational Decisions

### Catalog Source: Approach B — Own Vector Index
Build and own the product catalog by crawling brand sites directly. Embed product descriptions
(and eventually images) into a vector index. Provides richer, more controlled data than
affiliate APIs. No built-in affiliate commission — need to implement affiliate links (UTM
tracking + affiliate program enrollment) separately on top of the crawled catalog.

**Implications:**
- First milestone is now: "Can I crawl Aritzia/Uniqlo/Gap and extract clean product data?"
  (not "does Shopstyle API have this item?")
- Crawling ToS review required before scraping production brand sites
- Incremental refresh schedule needed (crawl on new-arrivals cadence, not full re-index daily)
- Affiliate commission still viable: link out with affiliate tracking even if catalog is self-hosted

### Mode: SCOPE EXPANSION
Greenfield startup. Building the full system from scratch.

### Pre-Build Locks (confirmed 2026-05-23)
- **Initial crawl targets**: Aritzia + Gap + Uniqlo (Phase 1). Madewell + Everlane in Phase 1.5.
- **MVP distribution**: Invite-only. Onboard Rosa and Isy manually first. No public sign-up until core search quality is validated.
- **Brand score initialization**: Selected brands start at 0.7 affinity (warm prior). Non-selected brands at 0.5 (neutral). Validate K-factor and initial values via ELO closed-loop test before shipping (test #6 in First Things First).

## Vision

### 10x Check
The 10x version of Ink isn't a search tool. It's a style intelligence layer. Ink knows
what you own, tracks what you've bought, watches what drops from your brands each week, and
builds a taste profile so accurate that it surfaces items you'd want before you know to search
for them. You open the app not because you need something — you open it because it shows you
what landed this week that fits your aesthetic.

### Platonic Ideal
You never search for clothes again. You set your brands once. You do a few A/B comparisons.
Then Ink knows your aesthetic well enough to send you one email a week: "3 things you'd love
dropped this week." Each item is from a brand you trust, in materials you prefer, in silhouettes
that match your vibe. When you buy something, Ink tracks it and updates your profile. When you
save something you didn't buy, Ink remembers and alerts you when the price drops.

The experience on first use: you upload a screenshot of a dress you saw on Instagram. Ink
extracts the garment attributes, searches your brands, and shows you 10 options from brands
you actually buy from — with a one-line note on each: "100% linen · relaxed silhouette · matches
your vibe." You tap "Find similar" on the closest one. Three iterations and you've found it.

## Accepted Scope (added to this plan)

Core (from design doc, Phase 1):
- Brand selection onboarding (user picks their trusted brands from pre-crawled list)
- Style questionnaire — 5 questions that map directly to taste profile dimensions:
    Q1: "Pick your silhouette" (image grid: relaxed/oversized/fitted/structured) → silhouette_pref
    Q2: "Which materials do you prefer?" (multi-select: cotton/linen/silk/wool/other) → material_pref
    Q3: "What's your usual price range per top?" (slider $20-$200) → price_sensitivity decile
    Q4: "Which brands do you buy from most?" (pre-populated from brand selection) → brand_scores init
    Q5: "Pick your preferred aesthetic" (image grid: minimal/classic/casual/eclectic) → style_cluster
    Answers map to taste profile initial values before any A/B comparisons happen.
- Text search: describe item → LLM re-rank → results from your brands
- Vector index: own the catalog via brand site crawling + embedding
- Material badge extraction and display
- Results grid: brand · name · material badge · price · "Why this matches you" annotation

Phase 2 (from design doc):
- A/B comparison interface ("Which fits your vibe better?")
- ELO-style taste profile (dimensions: silhouette, material, brand affinity, price sensitivity)
- Preference-weighted re-ranking (match_score × preference_affinity)
- Profile summary displayed on search home screen

Accepted expansions (from this CEO review):
- **Weekly drops digest**: Weekly email showing new arrivals from user's brands that match taste profile. Requires: new-arrivals crawl cadence, email cron, Postmark/Resend integration.
- **Visual search**: Image upload → GPT-4V/Claude extracts garment description → existing search pipeline. Requires: image upload/storage (S3 presigned URL), vision API call (~$0.005-0.015/query).
- **"Why this matches you" annotation**: LLM re-rank prompt returns match reason per result. Shown as one-line tag on result cards. Fallback: omit if LLM returns generic/empty reason.
- **Instagram/Pinterest taste import**: Connect social account → extract style priors from public posts → augment (not replace) the questionnaire-derived taste profile. Onboarding flow: questionnaire is mandatory (fills profile immediately); Instagram import is optional and adds additional signals on top. Start Meta API app review immediately. If approval arrives before MVP launch, enable at launch. If not, launch without it and add in a Phase 1.5 update. Do not block MVP launch on Meta API approval.
- **"Find similar"**: Extract garment attributes from a clicked result via LLM (silhouette, material, brand tier, price range, key construction details). Run as new search query through the same vector + re-rank pipeline. UI: "Find similar" button on each result card. Loop behavior: user explicitly initiates each "Find similar" click — no auto-recursive suggestions. Each click registers as an implicit positive signal on that item's attributes (updates taste profile in same ELO step as explicit A/B comparisons).

## Open Questions Requiring Resolution Before Code

1. **Crawling legal review**: Which brands allow product data crawling under their ToS?
   Aritzia, Gap, Uniqlo ToS must be reviewed before crawling production. Alternative:
   reach out directly for product feed access (CSV). Direct feeds are faster and more reliable
   than scraping.

2. **Vector search stack**: Pinecone vs pgvector vs Qdrant for the product vector index?
   Given early scale (~10K-100K SKUs initially), pgvector on a Postgres instance is likely
   sufficient. Pinecone only needed at 1M+ SKUs with high query volume.

3. **Instagram API app review**: Apply immediately at developers.facebook.com.
   Required permissions: `instagram_basic`, `pages_read_engagement` (for reading user's
   public posts). Review timeline: 6-8 weeks. Build questionnaire flow as the primary
   onboarding path while waiting.

4. **Revenue model**: No affiliate API = no built-in commission structure. Implement:
   - Affiliate program enrollment (ShareASale, Rakuten LinkShare, Impact) for each brand
   - UTM tracking on all outbound links (utm_source=ink, utm_campaign={search_query_hash})
   - Attribution: affiliate network handles 30-90 day conversion window tracking. Ink does not
     need to track post-click behavior server-side — affiliate programs report conversions via
     dashboard/API. MVP metric: click-through rate (Ink → brand site) as proxy for revenue
     viability. Phase 2: negotiate direct conversion API or pixel-based attribution with brands
     that convert at >5% CTR (indicates strong fit, worth deeper partnership).

5. **Crawl refresh cadence**: New arrivals at Aritzia/Uniqlo appear ~weekly. Full re-index
   is expensive. Strategy: RSS/sitemap diff to detect new product pages, crawl only new/changed
   pages. Gap (fast fashion cadence) may need daily diff.

6. **Embedding model**: text-embedding-3-small (OpenAI) vs voyage-code-3 (Voyage) vs
   native Claude embeddings for garment descriptions? voyage-code-3 is already in use in
   gstack for code search. For fashion, a general embedding model should suffice at MVP.
   Test precision before committing.

## Architecture (Updated for Approach B)

```
USER ONBOARDING
  ├── Brand selection (user picks from pre-crawled brand list)
  ├── Instagram/Pinterest taste import (optional, requires Meta API approval)
  │     └── Fallback: style questionnaire (3-5 questions)
  └── Initial taste priors from import or questionnaire

CATALOG INFRASTRUCTURE (Approach B)
  ├── Brand site crawler (Playwright or Scrapy)
  │     ├── Respects robots.txt and ToS (legal review required first)
  │     ├── Extracts: name, description, price, material, images, URL, brand
  │     └── Incremental: sitemap diff, crawl only new/changed pages
  ├── Embedding pipeline
  │     └── text-embedding-3-small or voyage on {name + description + material}
  ├── Vector store: pgvector (MVP) → Pinecone at 1M+ SKUs
  ├── Refresh cadence: weekly full + daily new-arrivals diff
  └── New-product discovery: sitemap monitoring (XML) + /new/ collection page crawl
        Aritzia: /en-US/new-arrivals, Gap: /new-arrivals, Uniqlo: /us/new
        Per-brand URL config required. Sitemap diff handles most brands;
        /new/ page crawl catches brands with stale sitemaps (Gap).

SEARCH FLOW
  ├── Text input: "cotton tie-back shirt, high collar, one tie"
  │   OR Visual input: image upload → GPT-4V → extracted description
  ├── Brand filter: All selected brands / single brand
  ├── Vector similarity search → top 50 raw candidates
  ├── LLM re-ranking: garment attribute precision match
  │     Input: user description + 50 candidates (descriptions ~60 words each)
  │     Output: llm_relevance_score (0.0-1.0, 1.0=exact attribute match) per candidate
  │             + match_reason per result (1 line, e.g., "Cotton + high collar + tie-back found")
  │     Terminology: three distinct scores exist in the system:
  │       vector_similarity_score — cosine distance from vector DB (used to pull top 50)
  │       llm_relevance_score — LLM garment-attribute match (used to rank top 10 from 50)
  │       final_ranked_score = llm_relevance_score × preference_affinity (for signed-in users)
  │       llm_relevance_score and final_ranked_score are internal only, never shown to user
  │     Cost: ~$0.015-0.03/query (Claude Haiku)
  │     Visual search adds: image upload → GPT-4V extracts description → same pipeline
  │       Cost: ~$0.005-0.015 extra per visual query (GPT-4V image processing)
  ├── Material badge extraction
  │     Primary: explicit material field from crawled HTML (e.g., <span class="fabric">cotton</span>)
  │     Fallback: LLM parses product description for material mention
  │     If material absent or ambiguous: badge omitted (not shown as "unknown")
  │     Crawl prototype (#2 in First Things First) measures what % of products have explicit
  │     material fields; if <70%, implement LLM fallback at crawl time, not query time
  ├── "Why this matches you" annotation (from LLM re-rank output)
  └── Results grid: brand · name · material badge · price · match annotation
        └── "Find similar" button → extract attributes → new search

A/B COMPARISON (post-results)
  ├── Pick 2 results: "Which of these fits your vibe better?"
  ├── Binary signal → update taste profile (ELO-style)
  │     Schema: {
  │       user_id,
  │       brand_scores: { Aritzia: 0.8, Uniqlo: 0.7, ... },        // per-brand affinity
  │       material_pref: { cotton: 0.9, linen: 0.7, polyester: 0.1 }, // categorical
  │       silhouette_pref: { relaxed: 0.8, fitted: 0.4, oversized: 0.6 }, // categorical
  │       price_sensitivity: 4,  // decile 1-10 (1=very price sensitive, 10=price insensitive)
  │       comparisons_count: 12
  │     }
  │     HOW DIMENSIONS ARE MEASURED: each product in the catalog has these attributes
  │     extracted by LLM at crawl time and stored as structured fields:
  │       { material: "cotton", silhouette: "relaxed", brand_tier: "mid", price_decile: 4 }
  │     When user picks item A over item B in A/B comparison:
  │       - item A's brand affinity score += K-factor × (1 - current_score)
  │       - item B's brand affinity score -= K-factor × current_score
  │       - same delta applied to material and silhouette dimensions
  │     ELO params: start each dimension at 0.5 (neutral), K-factor 0.1 (conservative —
  │     validate via closed-loop test during pre-code testing phase), clamped [0.0, 1.0]
  │     Unseen brand: initialize at average of all known brand scores, - 0.1 confidence penalty
  │     Unseen material/silhouette: initialize at 0.5 (neutral)
  │     Final re-rank: final_ranked_score = llm_relevance_score × (0.4×brand_aff +
  │                    0.3×material_match + 0.2×silhouette_match + 0.1×price_fit)
  │     Profile stabilizes ~20 comparisons. UI shows: "Your profile is built — you can keep
  │     comparing to refine it, or start browsing." (at comparisons_count == 20)
  │     "Find similar" clicks = implicit positive signal, same ELO update as explicit A/B
  ├── Skip option (skip does not update profile)
  ├── Profile summary shown on search home screen
  ├── A/B COMPARISON TRIGGER: shown after user clicks through to a product and returns
  │     "You looked at that one. Which of these fits your style better?"
  │     Never interrupts mid-search flow. Skip always available.
  └── EXPLICIT BRAND REMOVAL: user deselects a brand in settings = hard filter.
        That brand's products never appear. ELO handles implicit preferences;
        explicit removal overrides ELO. Historical A/B data retained (not deleted).
        If user re-adds brand: brand_score restored to 0.7 (same as onboarding).

WEEKLY DROPS DIGEST
  ├── New-arrivals diff runs Sunday 2am UTC (after weekly full re-index completes)
  ├── New items appear in digest within 24 hours of catalog crawl
  ├── Match new items against each user's taste profile (same weighted score as search)
  ├── Email: top 3-5 new arrivals that match user's vibe (sent Sunday morning)
  └── Infrastructure: weekly cron + Postmark/Resend (no overlap with daily new-arrivals diff)

INSTAGRAM/PINTEREST TASTE IMPORT
  ├── OAuth flow with Meta (pending API review — apply now)
  ├── Fetch user's public posts + saved items (last 50 posts)
  ├── Extract garment attributes from each image/caption via GPT-4V
  │     Extract: primary material, silhouette type, brand (if visible), price tier
  │     Low-confidence images (blurry, no garment visible): skip, do not downweight
  ├── Initialize taste profile from distribution of extracted attributes:
  │     If 7/10 posts show cotton → material_pref[cotton] = 0.7 + 0.5×0.5 = 0.85
  │     (i.e., extracted frequency × 1.0 + neutral_prior × 0.5, normalized to [0,1])
  │     Minimum 5 extractable images required to use import; else fall back to questionnaire
  └── MVP flow: questionnaire mandatory → Instagram import optional (augments, does not replace)
```

## UX Decisions (from Section 11 review)

- **Visual search entry point**: camera icon inside the search bar (right side). Same pattern as Google Lens. Don't make it a separate tab.
- **"Why this matches you" annotation**: one-line muted text below product name, above price. Never tooltip — invisible on mobile.
- **"Find similar" affordance**: text link below each result card (not a button). Subtle. Never competes with the primary "Shop at [Brand]" outbound link.
- **Brand onboarding UI**: pre-populated logo grid (Phase 1: Aritzia, Gap, Uniqlo) + text search for unlisted brands. Tap to select. Faster than type-only for known brands.
- **Empty state**: if a search returns 0 results, show: "No results from your brands for this search. Try broadening the description, or add more brands." Never a blank page.

## Security Decisions (from Section 3 review)

- **Image upload validation**: accept only binary file uploads (not URLs). Validate MIME type + file size at upload endpoint. Prevents SSRF.
- **Affiliate URL validation**: validate all outbound product URLs against an allowlist of expected brand domains before redirecting. Prevents crawled-product redirect hijacking.
- **Instagram OAuth tokens**: encrypted at rest. Use Postgres encrypted column or a secrets manager (e.g., Doppler, Railway secrets).

## Ongoing Quality Tests (from Section 6 review)

After MVP launch:
- **Weekly canary search** (manual): Rosa runs "cotton tie-back shirt, high collar, one tie" weekly. Validates top 3 results still include the right item. Catches catalog drift and LLM re-rank regression.
- **Drops pipeline health check**: after each Sunday drops run, log `new_items_found` and `new_items_matched_at_least_one_user`. If `new_items_matched == 0` for 3 consecutive weeks, the drops pipeline is broken.
- **A/B diversity check**: ensure A/B pairs surface items from different brands when possible. Same-brand comparisons generate no brand affinity signal.

## Opinionated Recommendations

**What this CEO review found that wasn't in the original design doc:**

**1. Approach B (own the vector index) changes the first milestone.** The original design said "run the Shopstyle API test in 2-3 hours." The right first milestone now is: "Write a 100-line Playwright script, crawl 50 Aritzia products, embed them, run 5 test queries." That takes 1 day, not 2 hours. But the data you get back is richer and the precision ceiling is higher. It's the right trade.

**2. The weekly drops email is the most underrated feature in this plan.** Visual search and Instagram import are exciting. The weekly drops email is what makes Ink a weekly ritual instead of a search tool you use once a month. Build it in Phase 1, not Phase 2. It's 2-3 hours of code on top of the crawl infrastructure you're already building.

**3. The A/B comparison trigger matters more than the A/B comparison mechanism.** You can have the most elegant ELO model in the world, but if users never see the comparison prompt, the taste profile never improves. Show it after click-through — the user has just expressed real interest in something, and "which of these fits your style better?" is the most natural follow-on question at that moment.

**4. Instagram import is accepted in scope, but don't let it block the MVP launch.** The Meta API review takes 6-8 weeks. The questionnaire works well enough to validate that users engage with the product. Ship with questionnaire, add Instagram import in Phase 1.5 when the API review comes through.

**5. The existential risk is still catalog coverage.** Not LLM re-rank quality. Not the ELO model. If you can't crawl Aritzia's product pages, there's no product. Do the crawl prototype test before writing a single line of application code. It takes 1 day and gives you the answer to the only question that matters.

**6. The differentiation against Daydream is time-sensitive.** Daydream has $50M. They will eventually add brand filtering and taste profiles. Ink's defensible advantage is the user's data accumulated in the taste profile — the longer a user has been using Ink, the better their results, and that advantage can't be copied by a competitor who arrives later. Ship fast. Accumulate data. The taste profile IS the moat.

## First Things First

Priority order before writing production code:

1. **Crawling legal review** (1-2 days): Review ToS for Aritzia, Gap, Uniqlo, Madewell, Everlane.
   Decision gate: if ToS is silent on product scraping, email brand partnership teams with a
   specific request for product feed CSV access (draft email template before contacting). Max
   wait: 1 week. If no response in 1 week, proceed with scraping (assume permission by silence).
   Only block on an explicit "no scraping" clause in ToS. Fallback if brands say no: CSV feed
   partnership (2-4 week delay) or fall back to Approach A (affiliate API) for that brand.

2. **Crawl prototype** (1 day): Write a proof-of-concept Playwright crawler for Aritzia's product
   catalog. Verify: name, description, material, price, image URL, product URL extractable?
   Measure: what % of products have an explicit material field? If <70%, implement LLM material
   extraction at crawl time (not query time) — bake this decision into the architecture before
   building the production crawler.

3. **Vector search precision test** (1 day): Embed 100 Aritzia products using OpenAI
   text-embedding-3-small. Run 10 test queries (including "cotton tie-back shirt, high collar,
   one tie"). Measure: is the correct item in the top 50 results for at least 7/10 queries?
   (70% pass rate = proceed.) If <70%: re-run with Voyage-3 embeddings. If Voyage-3 also fails:
   add structured garment attribute fields to the crawl schema (not just free-text embeddings)
   and retest. Document precision by category (shirts, dresses, etc.) for calibration.

4. **LLM re-rank precision test** (2 hours): Take the top 50 vector results from test #3.
   Re-rank with Claude Haiku. Does the re-rank correctly surface the "one tie at back, high collar"
   item and demote wrong-tie-placement results? This is run AFTER test #3 passes — if vector
   search doesn't surface the right candidates, LLM re-rank can't help.

5. **Instagram API app review application** (2 hours): Apply at developers.facebook.com while
   tests 1-4 run. Permissions: instagram_basic, pages_read_engagement. 6-8 week review window
   starts on submission. Target MVP launch: 6 weeks after tests 1-4 pass (rough internal
   milestone — adjust based on crawl results). If Instagram import approved before launch:
   enable at launch. If not: launch with questionnaire-only onboarding, add import in Phase 1.5.
   Contingency for cold start without social import: questionnaire Q1-Q5 provides enough signal
   for usable Day 1 results (validated by closed-loop test #6 below).

6. **ELO K-factor closed-loop validation** (1 week, run in parallel with build): Recruit 5 beta
   users. Have each do 20 A/B comparisons. Manually review whether the weekly drops email after
   20 comparisons contains items they'd actually buy. If K=0.1 is too conservative (scores don't
   move enough), test K=0.2 or K=0.3 before shipping. Target: at least 3/5 users agree the drops
   email is accurate.

7. **GPT-4V visual search reliability test** (2 hours): Collect 20 Instagram screenshots of
   outfits (from Isy's actual use case: influencer posts). Run each through GPT-4V and ask it to
   extract garment attributes. Measure: for how many screenshots does it produce an actionable
   description (one the search pipeline can use)? Target: >18/20 (90%). If <90%: test Claude
   vision as fallback, add structured prompt with few-shot examples. Do not ship visual search
   without passing this test.

If tests 2, 3, and 4 pass: the product works. Start building.
If test 3 fails at 70% with both embedding models: store structured attributes (silhouette,
  material, collar type, back detail) as separate searchable fields at crawl time. More work,
  better precision. Reassess before building production crawler.
If test 2 fails (can't crawl legally or technically): contact brands for CSV product feed access
  (draft the email in test #1). This adds 2-4 weeks but gives cleaner data.
If test 4 fails: the LLM can't understand garment construction at this precision level. This
  invalidates the core claim against Daydream. Revisit prompt engineering with more examples
  before deciding the approach is wrong.
